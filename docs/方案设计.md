# Chromium Minimal Runtime 方案设计

## 1. 背景

目标不是做一个普通浏览器，而是做一个面向数据采集的最小浏览器运行时。它只保留加载网页、执行 JavaScript、渲染 Canvas/WebGL、网络请求、Cookie/Storage、自动化控制和数据提取能力。

Chrome 产品层非常重，但现代网站对浏览器能力依赖很强。如果完全自研 DOM、JS、Canvas、Fetch、Storage、Shadow DOM、Service Worker，会很快变成重新造 Chromium。因此，本方案选择保留 Chromium 核心能力，裁剪产品功能。

## 2. 总体架构

```text
Collector App
   |
   | API: goto / click / input / extract / screenshot
   v
BrowserRuntime
   |
   | Profile / Fingerprint / Proxy / Cookie / Storage
   v
Chromium Content Layer
   |
   | WebContents / NavigationController / RenderFrameHost
   v
Blink + V8 + Network + Skia + ANGLE
```

## 3. 核心模块

### 3.1 BrowserRuntime

负责统一管理：

- 浏览上下文
- Profile
- 有头/无头模式
- 页面生命周期
- 网络上下文
- 自动化 API
- 数据采集任务

### 3.2 FingerprintProfile

负责加载和应用指纹配置：

- User-Agent
- Platform
- Language
- Timezone
- Screen
- Canvas
- WebGL
- AudioContext
- Permissions
- Plugins
- MediaDevices
- TLS/HTTP2

### 3.3 AutomationAPI

提供采集动作：

- `goto(url)`
- `click(selector)`
- `input(selector, value)`
- `waitSelector(selector)`
- `evaluate(js)`
- `extract(selector)`
- `screenshot(path)`
- `dumpDom()`

### 3.4 Storage

使用 Chromium 自带 StoragePartition，确保 Cookie、LocalStorage、IndexedDB 和 Cache 行为接近真实浏览器。

## 4. 有头/无头统一原则

不要使用两套引擎。

```text
错误方式：
Headful = normal chrome
Headless = chromium headless mode
```

正确方式：

```text
BrowserRuntime + WebContents + NetworkContext + StoragePartition 始终相同
有头：创建窗口并显示 surface
无头：不创建窗口，但仍走同一套渲染和网络流程
```

## 5. 为什么选择 content_shell/headless_shell

`content_shell` 是 Chromium 自带的最小浏览器壳，已经具备：

- 页面加载
- Blink/V8
- 网络
- Storage
- DevTools
- 基础渲染

它比完整 Chrome 轻很多，适合作为最小采集浏览器起点。

## 6. 风险

- Chromium 编译仍然很重。
- 版本升级成本高。
- TLS/HTTP2 指纹深度改造复杂。
- 删除模块可能破坏网站兼容性。
- 反爬检测点不是单点，而是跨 JS、网络、渲染、行为的一致性检测。

## 7. 推荐开发顺序

1. 先跑通原生 `content_shell`。
2. 加最小 API：goto、evaluate、screenshot。
3. 加 Profile 配置加载。
4. Hook Navigator/Canvas/WebGL。
5. 统一有头/无头。
6. 加任务脚本和 SQLite 保存。
7. 再开始裁剪模块。
