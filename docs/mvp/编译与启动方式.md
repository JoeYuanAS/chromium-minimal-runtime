## 源码获取方式

当前思路不是下载官方 `content-shell.zip` 二进制，而是用最小历史的 Chromium 源码：

- `--depth=1`：不拉完整 git 提交历史。
- `--filter=blob:none`：按需拉文件内容。
- `sparse-checkout`：起步只展开 `content/shell`、`content/public`、`build`、`tools` 等路径。

入口脚本：

```bash
scripts/fetch_chromium_sparse_source.sh
```

默认 commit：

```text
e0488508e67c7243b2f21e478727d1989f9d1e71
```

注意：这个 sparse checkout 适合起步读代码和改 `content_shell`。要真正编译 `content_shell`，Chromium 的 DEPS 和 GN 依赖会继续拉入大量源码和第三方依赖，不能只保留 `content/shell` 那几个目录。

## macOS app 启动修补

直接从编译产物提取后，曾遇到两个问题：

1. Framework 依赖 `@loader_path/Libraries/libtest_trace_processor.dylib`，但提取版没有带这个 dylib，导致启动时 `dlopen` 失败。
2. `content_shell` 启动会在 `Contents/MacOS/content_shell.log` 写日志，导致已签名 bundle 运行后被污染，后续 `codesign --verify` 失败。

当前处理方式：

- 把真实 Chromium 可执行文件放到：

```text
Contents/MacOS/Content Shell.bin
```

- 增加一个很小的 Mach-O launcher 作为 app 入口：

```text
Contents/MacOS/Content Shell
```

launcher 源码在：

```text
/Users/zy.yuan/Develop/browser-runtime-projects/chromium-minimal-runtime/src/content_shell_app_launcher.c
```

launcher 做的事情：

- 找到同目录下的 `Content Shell.bin`。
- 如果用户没有显式传 `--log-file`，自动追加：

```text
--log-file=/tmp/content_shell.log
```

- 设置环境变量：

```text
CHROME_LOG_FILE=/tmp/content_shell.log
```

- `execv()` 到真实 `Content Shell.bin`。

这样 `open` 或双击 app 时仍然是原生 Mach-O 入口，LaunchServices 可以正常启动，同时日志不会写进 app bundle 内部。

## launcher 编译方式

当前使用系统 clang 编译：

```bash
APP="/Users/zy.yuan/Develop/browser-runtime-projects/chromium-minimal-runtime/output/content-shell-minimal/Content Shell.app"
MACOS="$APP/Contents/MacOS"

if [ ! -f "$MACOS/Content Shell.bin" ]; then
  mv "$MACOS/Content Shell" "$MACOS/Content Shell.bin"
fi

/usr/bin/clang -O2 -Wall -Wextra -arch arm64 \
  "/Users/zy.yuan/Develop/browser-runtime-projects/chromium-minimal-runtime/src/content_shell_app_launcher.c" \
  -o "$MACOS/Content Shell"
```

## 签名方式

当前是本地开发用 ad-hoc 签名：

```bash
codesign --force --sign - "$MACOS/Content Shell.bin"
codesign --force --deep --sign - "$APP"
codesign --verify --verbose=6 "$APP"
```

这不是发布签名，也不是 notarization。它只保证本机开发和验证时 app bundle 结构是自洽的。

## 当前启动行为说明

`content_shell` 是有界面浏览器壳，不是一次性 CLI 工具。启动成功后通常会持续运行，不会像 `curl` 一样立刻退出。

之前测试过的 `--dump-dom`、`--run-web-tests`、`--dump-render-tree`、`--run-layout-test` 在当前形态下没有作为稳定的 headless dump 路径使用，表现为进程常驻或超时。MVP 阶段建议先把它当作有头 `content_shell` + DevTools 调试端口验证。
